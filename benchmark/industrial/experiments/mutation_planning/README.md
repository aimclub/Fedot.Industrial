# Парное сравнение качества и вычислительных затрат

`quality_cost.py` проверяет уже полученные записи запусков и строит отчёт.
Он не обучает модели, не загружает данные и не меняет настройки эксперимента.
Структурные показатели, включая число уникальных графов, не доказывают улучшение
качества и не участвуют в приёмке.

## Входные записи

Файл JSON должен содержать объект с `schema_version` равным
`industrial_mutation_quality_cost@1` и массивом `records`.
Каждая запись содержит следующие поля:

| Поле | Требование |
| --- | --- |
| `task`, `scenario`, `dataset`, `metric`, `budget_id` | Непустые строки; `budget_id` обозначает одинаковый вычислительный бюджет для обоих режимов |
| `seed` | Целое число, не `bool` |
| `mode` | `legacy` или `planned` |
| `greater_is_better` | Строго `bool` |
| `status` | `succeeded` или `failed` |
| `quality` | Конечное число при успехе, `null` при неудаче |
| `train_seconds` | Конечное неотрицательное число, включая затраченное время неудачного запуска |
| `predict_seconds` | Конечное неотрицательное число; при неудаче допускается `null` |
| `peak_memory_bytes` | Необязательное поле: неотрицательное целое число или `null` |
| `memory_scope` | Явное название области измерения памяти; `null` допускается только без измеренной памяти |
| `source` | Необязательный объект JSON с происхождением записи, версиями, ошибкой и другими сведениями |

`python_tracemalloc` учитывает выделения памяти Python, а не всю память процесса,
нативных библиотек или CUDA. Разные области измерения нельзя сравнивать как одну
величину. Без измерения память остаётся `null` / `not_assessed`.
Значения `NaN`, бесконечности и логические значения вместо чисел запрещены.
Дополнительные поля JSON сохраняются как свидетельства, но не влияют на приёмку.

Пары формируются по `scenario/dataset/seed/metric/budget_id`. Повтор записи того же
режима внутри пары вызывает ошибку. Несовпадение `task`, `greater_is_better` или
`memory_scope` делает пару несовместимой и блокирует приёмку. Различия бюджетов
создают неполные пары, а не сравнение запусков с разными условиями.
Достоверность обозначений набора данных и бюджета обеспечивает источник записей.

## Использование

Запуск по пути файла не загружает зависимости родительского пакета:

```powershell
.local/evo02-tests/Scripts/python.exe benchmark/industrial/experiments/mutation_planning/quality_cost.py records.json --output-json report.json --output-markdown report.md
```

Каталоги выходных файлов должны существовать. Без параметров вывода JSON
печатается в стандартный поток. Ошибки формата завершают CLI с кодом `2`;
код `0` означает построение отчёта, а не успешную приёмку.

Чистые функции модуля: `validate_run_record`, `summarize_quality_cost`,
`render_quality_cost_markdown`. Входные объекты не изменяются. Разность качества
ориентирована так, что положительное значение означает преимущество `planned`.
Разности затрат равны `planned - legacy`, отношения равны `planned / legacy`.
При нулевом знаменателе, переполнении или округлении положительного отношения до
нуля результат остаётся `null` с объяснением.
Результаты разных наборов данных и метрик не усредняются.

По умолчанию приёмка имеет статус `not_assessed`. Для её проверки нужно явно
передать **оба** параметра: абсолютный допуск ухудшения качества `quality_tolerance`
и непустой объект `cost_constraints`. В CLI их читает `--criteria criteria.json`.
Допустимые ограничения: `max_train_seconds`, `max_predict_seconds`,
`max_peak_memory_bytes`, `max_train_ratio`, `max_predict_ratio`, `max_memory_ratio`.
Все пределы задаёт пользователь, встроенных порогов нет. Отношения используют
одинаковую ориентацию `planned / legacy`. Ограничения отношений проверяются по
исходным значениям, чтобы округление отображаемого отношения не скрыло превышение.
Допуск качества также проверяется по исходным числам, без скрытого запаса на
погрешность; для `float` учитываются именно переданные двоичные значения.

Приёмка требует успешных совместимых пар и определённых значений всех проверяемых
величин. Неудачи, пропущенные режимы, пустой вход и неопределённые проверки дают
`not_assessed`, а не успех. Неизмеренная память блокирует только проверку
ограничения памяти; приёмка без такого ограничения ничего не утверждает о памяти.
Вывод относится только к представленным запускам: полностью отсутствующие
сценарии, повторности и различия условий, не отражённые в записях, не выявляются.

Абсолютный допуск имеет единицы выбранной метрики. Для разных метрик и масштабов
целевой переменной следует задавать отдельные критерии и строить отдельные отчёты.

## Короткая проверка с обучением

`quality_runner.py` выполняет ограниченный поиск одношаговых изменений, а не
полный эволюционный поиск. Настройки находятся в `quality_defaults.json`.
По умолчанию возвращается только план, без записи файлов и обучения:

```powershell
.local/evo02-tests/Scripts/python.exe -m benchmark.industrial.experiments.mutation_planning.quality_runner --output-dir .local/quality_trial
```

Для обучения нужна отдельная копия FEDOT с явно применёнными исправлениями из
`fedot_ind/integration/fedot/compat`. Путь импорта и контрольные суммы проверяются:

```powershell
$env:PYTHONPATH="$PWD/.local/worktrees/fedot-evo04-feature-smoke;$PWD"
.local/evo02-tests/Scripts/python.exe -m benchmark.industrial.experiments.mutation_planning.quality_runner --output-dir .local/quality_trial --compatibility-worktree .local/worktrees/fedot-evo04-feature-smoke --execute
```

Оба режима получают одни данные и одинаковое число попыток, включая исходный
конвейер. Данные разделены на обучение, выбор кандидата и окончательную проверку.
Только проверочная часть используется для выбора модели; итоговая тестовая часть
не передаётся в обучение или выбор. Индексы частей и контрольная сумма данных
сохраняются. Порядок режимов чередуется между начальными значениями.

Время обучения включает предложения мутаций, обучение кандидатов и проверочный
выбор. Неудачная попытка тоже расходует бюджет; число успешно обученных кандидатов
может различаться. Измерение `python_tracemalloc` не гарантирует полного учёта
выделений NumPy и PyTorch и не измеряет всю память процесса. Первый вызов может
включать загрузку реализаций.
Это проверка протокола, а не надёжное измерение производительности.

Записи сохраняются после каждого режима в `records.json`; итоговые файлы —
`quality_cost.json` и `quality_cost.md`. Существующие результаты не перезаписываются.
Ошибки кандидатов не подменяются искусственными метриками. Приёмка остаётся
`not_assessed`, пока отдельно не заданы критерии. Прогнозирование и полные
обученные популяции в этот короткий набор не входят.
