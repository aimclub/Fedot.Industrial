# План развития эволюционных бенчмарков

25 ноября 2026. Согласованный порядок: **TSC, затем TSER, затем расширение TSF**. Это план и спецификации, не разрешение на запуск. Исполняемый код, конфигурация Torch, исходная серия B и её артефакты не меняются. Официальный TEST не используется; вычислительные допуски требуют отдельного указания.

После вливания #320 чистая ветка `codex/evbench-evolution-pilots` создана от
`8ef3ab15c63a77c9f363cc1e77b1cc4e490427c5`. Прежние незакоммиченные правки
в неё не перенесены. Спецификации ниже сохранены как исходная постановка.
Для EVBENCH-01 проверены контрольные суммы четырёх файлов TRAIN и всех
четырёх разбиений на scikit-learn 1.3.2. Обучение на этом этапе не требуется.

Прежний допуск B проверен по сохранённому состоянию сервера: восемь поисков
и четыре итоговые оценки завершены, отказов кандидатов нет. Это историческое
подтверждение, а не повторный запуск на новой базе. Исполнитель
`tsf_variant_b` отсутствует в `main`; для EVBENCH-06 его ревизию нужно
проверить и зафиксировать отдельно.

## Исходная база

- Рабочая ветка `industrial_release_1.0`, опорный коммит `9ad5bb28` (интеграция PR #357). Спецификация описывает **проверенную рабочую копию**, а не только этот коммит. В ней есть незакоммиченные адаптеры прогнозирования, каталог и исполнитель [варианта B](../experiments/tsf_variant_b/); эти изменения нельзя выдавать за содержимое `9ad5bb28` или включать в новые PR автоматически.
- В `pyproject.toml` FEDOT закреплён на коммите `d1875e7a1ba49c94d13c51d97ec78829bf459ca8`. Для воспроизводимости сохранить также происхождение фактически установленного FEDOT, GOLEM, Dask, Python и Torch. Не переносить выводы с одного окружения на другое без проверки.
- Исходный протокол: [TSC-пилот](tsc_evolution_pilot.md). Для TSER читать существующие источники [mutation_quality](../experiments/mutation_quality/protocol.json); его новый состав и разбиения ещё не зафиксированы. Для прогнозирования опираться на [сверку источников TSF](tsf_expansion.md), не на значения старых таблиц без сопоставимых разбиений.
- До первого кодового PR выполнить **P0, фиксацию базы**: сохранить квитанцию действующего допуска B, контрольные суммы используемых изменений и результат сверки зависимостей; отделить согласованные изменения от посторонних. Чистая база первого PR должна содержать только необходимые изменения исполнения, либо опираться на уже принятую копию. Если допуск B не пройден, можно готовить независимый слой TRAIN и локальные контракты, но не запускать новые серии на непроверенном исполнителе.
- Целевая ветка цепочки: согласованная интеграционная ветка Industrial, в текущем плане `industrial_release_1.0`. Ниже базы указаны как **зависимости**, а не как вымышленные SHA. Перед открытием каждого PR записать фактический базовый SHA, целевой ref, проверяемый diff и идентификатор спецификации. Не направлять в `main` без отдельного решения.
- Перед кодом отдельно зафиксировать открытые решения: точные настройки планировщика эпох и предел времени подбора TSC; источники и разбиения TSER; подтверждённый TRAIN Tourism и полный список рядов TSF. Ни одно из них не следует из успеха исходной серии B. Требования к данным, модели, вычислительному допуску и публикации проверяются независимо.

## Решения о структуре

| Как устроено сейчас | Варианты | Выбранное направление и ограничение |
| --- | --- | --- |
| [`search`](../experiments/tsf_variant_b/search.py) строит поколения, вызывает Dask, минимизирует RMSE, ведёт историю и открывает банк весов в одной процедуре. | Скопировать весь исполнитель; обобщить сразу TSC/TSER/TSF; выделить только повторяемые решения по мере появления второго потребителя. | Сначала сделать предметный TSC-исполнитель. Повторно использовать `GraphDevicePolicy`, `DaskEvaluationSession`, `run_guarded`, `OptHistory` и функции итогов. Общую сортировку, бюджет и запись вынести только при доказанном совпадении поведения. Не переделывать три работающих входа ради одинакового вида файлов. |
| Мутационные исследования уже умеют загружать [запечатанные данные](../experiments/mutation_quality/execution/frozen_data.py); публичные загрузчики TSC/TSER читают пару TRAIN/TEST. | Добавить флаг всем публичным загрузчикам; использовать текущие изменяемые массивы напрямую; выделить подготовку входов пилота. | Пилот получает отдельно запечатанные части разработки и оценки. Заготовки `mutation_quality` использовать как образец, а публичное чтение TRAIN/TEST не менять. Единая метка объекта не подменяет проверку доступности меток по фазам. |
| `TrainingSession` общий; `ForecastTrainingPolicy` и `SelectionSplit` относятся к прогнозированию. | Расширить прогнозную политику флагами TSC/TSER; написать другой цикл обучения; адаптировать входы и цель к общему циклу. | Оставить общий цикл. Добавить политику обучения по объектам, затем адаптировать задачу и функцию потерь в TSER. Не переносить временные окна, кодировку классов или целевые масштабы между задачами. |
| Табличный и двумерный выходы `RecurrenceExtractor` различаются, текущий транспорт FEDOT допускает ранг до 3. | Поменять только тип каталога; передавать явно упакованное изображение с проверкой; расширить формат FEDOT. | Для пилота проверить явную обратимую упаковку между двумя выделенными узлами. Настоящий транспорт ранга 4 для произвольных операций является отдельным изменением FEDOT, не частью этого этапа. |

## Общие правила приёмки

1. Каждый PR закрывает указанный контракт независимо от результатов большой серии. Сначала минимальный синтетический пример и проверки отказов, затем тесты актуальной точки входа, только потом согласованный технический допуск. Ориентир для ревью: около 500 изменённых строк для сложного контракта, до 2 000 для однородного этапа. Не дополнять PR объёмными отчётами, сырыми данными или несвязанными исправлениями.
2. До чтения входов дешёвая валидация схемы, пути, роли, числовых пределов, типов и контрольных сумм. После подготовки сохранившийся план неизменяем: параметры поиска, модели, бюджеты, Torch и разбиения нельзя переопределять окружением или командой запуска. В параметрах команд разрешены только указанные каталоги и идентификатор плана. Оператор не может превратить `plan` в `run` одной скрытой настройкой.
3. Различать `rejected` до оценки, ошибку кандидата, тайм-аут, неподтверждённое завершение процесса, неполный поиск и итоговую оценку. Победитель из неполного поиска допустим как диагностика, не как проход допуска. Версия, SHA плана, входных файлов и исполняемой среды, история, решения о выборе и фактические устройства привязаны к одной квитанции. Длительности настройки, поиска и финального обучения записываются отдельно.
4. После реализации проверить новые предметные тесты и целевые наборы из действующих проверок: `python -m pytest tests/unit/integration/fedot -q`, `python -m pytest tests/unit/core/optimizer/evaluation -q`, обычные Unit Tests и [Platform contracts](../../../.github/workflows/platform_checks.yml). Проверить установленные пакеты вне рабочей копии, если добавлены поставляемые протоколы или каталоги. CPU-тесты проверяют контракт, но не подтверждают маршрут CUDA. Перед переносом сверить изменения и результаты проверок через `premerge-pr-review`.

На этом этапе выполнена только сверка исходного кода. Команды и критерии в спецификациях относятся к будущей реализации. Переход к измерению выигрыша возможен только после технической приёмки; он требует отдельной постановки, достаточного покрытия и заранее выбранного критерия.
