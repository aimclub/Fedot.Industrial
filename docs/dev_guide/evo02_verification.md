# EVO-02: типизированные настройки, состояния и ошибки

## Назначение

EVO-02 заменяет неявные словари, строковые состояния и неоднозначные ошибки в
контуре эволюционной оптимизации явными предметными типами. Внешняя форма старых
настроек остаётся совместимой, но преобразуется один раз на границе API. Внутри
оптимизатора используются только проверенные неизменяемые значения.

## Настройки

Каноническая схема имеет версию `industrial_evolution_config@1` и представляется
классом `EvolutionConfig`. Пример сериализованной формы:

```json
{
  "schema_version": "industrial_evolution_config@1",
  "random_seed": 42,
  "mutation": {
    "agent": "random",
    "strategy": "params_mutation_strategy"
  },
  "resource_budget": {
    "min_population_size": 10,
    "mutation_attempts_per_candidate": 50,
    "population_extension_attempts": 100
  },
  "execution_policy": {
    "initial_graphs_prevalidated": false,
    "retry_initial_population_without_timer": true,
    "diagnostics_output_dir": null
  }
}
```

`ResourceBudget` задаёт ограничения на построение популяции. `ExecutionPolicy`
описывает решения, связанные с повторной оценкой начальной популяции,
предварительной проверкой начальных графов и сохранением диагностики.

Функция `normalize_evolution_config` принимает:

- старый плоский словарь;
- канонический вложенный словарь;
- готовый `EvolutionConfig`;
- `None`, для которого применяются явные значения по умолчанию.

Неизвестные поля, неверные типы, неподдерживаемая версия схемы и противоречия
между старой и канонической формами накапливаются в `EvolutionConfigError`.
Каждое нарушение содержит устойчивый код, путь к полю, сообщение и исходное
значение. Строки `"true"` и `"false"` не преобразуются неявно в логические
значения.

`IndustrialRepositoryInitializer` выполняет нормализацию до создания
частично применённой функции `functools.partial`. Прямое создание
`IndustrialEvoOptimizer` и
`FedotEvoOptimizer` использует ту же границу; повторная передача готового объекта
не запускает повторный разбор.

## Состояния и ошибки

`EvolutionState` хранит текущую фазу и неубывающий номер поколения. Разрешённые
переходы образуют следующий граф:

```text
created -> initialising -> evaluating_initial -> evolving -> completed
    |             |                 |              |
    +-------------+-----------------+--------------+-> failed
```

Состояния `completed` и `failed` являются конечными. Обратный переход поколения
и недопустимая смена фазы приводят к `EvolutionTransitionError`.

`CandidateFailure` описывает ожидаемые причины недопуска кандидата:

- мутация не вернула `Individual`;
- проверяющая функция отклонила граф;
- проверяющая функция завершилась ожидаемой ошибкой проверки;
- граф уже присутствует в популяции.

Строковый заполнитель `'empty'` удалён. Исчерпание заданного числа попыток
построения кандидата теперь регистрируется как данные и не приводит к позднему
обращению к несуществующему полю `.graph`.

`EvaluationOutcome` представлен отдельными вариантами успешной, неуспешной и
повторно использованной оценки. Неуспешный вариант содержит `EvaluationFailure`
с кодом, типом ошибки и сообщением. Метаданные рабочих процессов используют
схему `industrial_evaluation_outcome@1`; прежние ключи `evaluation_error` и
`evaluation_error_type` временно сохраняются для совместимости.

Ожидаемые ошибки целевой функции перечислены явно и преобразуются в
`EvaluationFailure`. Ошибки среды, например `OSError`, не подавляются и не
подменяются нулевой приспособленностью. В обновлённом пути отсутствуют обработчики
`except Exception` и `except BaseException`.

## Проверки свойств

В зависимости для разработки добавлен `Hypothesis`. Для Python 3.10 закреплён
совместимый диапазон `>=6.100,<6.113`. Временное разрешение зависимостей,
использованное при проверке EVO-02, выбрало версию `6.112.5`.

Проверки свойств подтверждают:

- круговой переход `EvolutionConfig -> dict -> EvolutionConfig`;
- детерминизм и идемпотентность нормализации;
- эквивалентность старой и канонической форм настроек;
- круговой переход вариантов `EvaluationOutcome` через метаданные.

Отдельные тесты проверяют накопление независимых нарушений, конфликт двух форм
одного поля, конечность состояний, монотонность поколения, приоритет причин
отклонения кандидата и отказ при повреждённых метаданных оценки.

## Явные случайные решения и жизненный цикл

Поле `random_seed` принимает неотрицательное целое число или `null`. При `null`
сохраняется прежнее поведение. Явное значение включает отдельные последовательности
для выбора родителей, отбора, скрещивания, мутаций и обучения адаптивного агента
в `IndustrialEvoOptimizer`. В `FedotEvoOptimizer` обёртки применяются к отбору,
скрещиванию и мутациям; остальные решения наследуемого цикла GOLEM остаются
за пределами этой гарантии.

`CandidateRandomness` задаёт адрес решения: начальное значение запуска,
название последовательности и номер попытки. Производное значение вычисляется
через SHA-256, а не через нестабильный Python `hash`. Адрес не содержит UUID,
идентификатор процесса или номер исполнителя. Неуспешная мутация также расходует
попытку. Для нового кандидата адрес сохраняется в метаданных
`candidate_randomness` со схемой `industrial_candidate_randomness@1`.

Операторы GOLEM используют глобальные генераторы Python и NumPy. Совместимая
обёртка временно устанавливает их состояние и обязательно восстанавливает его,
в том числе при ошибке. Блокировка защищает только участвующие в этом механизме
потоки. Счётчики попыток принадлежат координатору: одну обёртку не следует
одновременно вызывать из нескольких исполнителей.

Гарантия относится к последовательности решений при одинаковых входах,
порядке вызовов и результатах оценки. Она не обеспечивает побитовое совпадение
обучения на CUDA, соблюдение настенного времени или воспроизводимость
стороннего оператора с собственным неуправляемым генератором. Оценка моделей
не выполняется внутри области временного изменения генераторов.

Модельный тест на Hypothesis сопоставляет допустимые и запрещённые переходы
с независимым описанием состояний. Проверки публичного `optimise` проходят
инициализацию, оценку, отклонение повторного кандидата, завершение по бюджету
и ошибку оператора. После ошибки фаза становится `failed`, исходное исключение
сохраняется, а индикатор выполнения закрывается. После конечной фазы повторный
запуск запрещён. Если размер популяции уже достаточен, лишние мутации не вызываются.

Проверки включают реальные конструкторы обоих оптимизаторов и оператор мутации
GOLEM, повтор в отдельном Python-процессе, потоки с независимыми адресами,
сохранение метаданных и продолжение счётчика после сериализации.

### Повторная проверка после PR #318

Проверки выполняются с FEDOT `d1875e7a1ba49c94d13c51d97ec78829bf459ca8`,
закреплённым в `pyproject.toml`, и Hypothesis `6.112.5`. Локальная среда
`.local/evo02-tests` использует общие вычислительные зависимости, но отдельную
установку Hypothesis. Поэтому этот запуск не заменяет чистую установку всех
зависимостей в CI.

```powershell
$env:PYTHONPATH="$PWD/.local/worktrees/fedot-evo02-test;$PWD"
.local/evo02-tests/Scripts/python.exe -m pytest `
  tests/unit/core/optimizer `
  tests/unit/core/repository/test_industrial_dispatcher_extension.py `
  tests/unit/api/services `
  tests/unit/benchmark/industrial/experiments/test_evolution_observability.py `
  tests/unit/integration/fedot `
  --cov=fedot_ind.core.optimizer.randomness --cov-report=term-missing -q
```

Тесты не требуют внешних наборов данных, обучения моделей или доступа к CUDA.
Итог: **511 тестов прошли**, покрытие `randomness.py` по исполняемым строкам
составило **100%**. Четыре предупреждения относятся к устаревшим названиям
функций связи в `statsmodels`. Компиляция изменённых модулей и
`git diff --check` также завершились успешно.

## Сопоставление с EVO-01

Ниже сохранён исторический замер первой части EVO-02, до завершения PR #318.
Он не является новым измерением качества текущей ветки. Повторный запуск
тогда выполнялся командой:

```powershell
.venv\Scripts\python.exe -m benchmark.industrial.experiments.evolution_observability `
  --output-dir .local/evo02_baseline --execute
```

Результат совпал с исходным уровнем EVO-01:

| Сценарий | Состояние EVO-01 | Состояние EVO-02 |
|---|---|---|
| `tiny_classification` | `failed` | `failed` |
| `tiny_regression` | `not_observed` | `not_observed` |
| `tiny_forecasting` | `failed` | `failed` |

Для классификации в обоих запусках зарегистрированы 4 попытки мутации, 1
принятый кандидат, 8 неуспешных оценок `InvalidFitness` и значение
`valid_offspring_ratio`, равное 0,25. Отличается только фактическое время
выполнения. Следовательно, EVO-02 уточняет контракты и обработку ошибок, но не
скрывает алгоритмические проблемы, предназначенные для EVO-03 и EVO-04.
