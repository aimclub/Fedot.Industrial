# EVO-03: возможности операций и чистая проверка графа

## Назначение

EVO-03 отделяет правила допустимости графа от объектов FEDOT и GOLEM. Проверка
получает неизменяемый `GraphSpec` и возвращает полный `ValidationReport`.
Функция не обращается к репозиториям, не восстанавливает конвейер, не изменяет
граф и не прекращает работу после первого нарушения.

Изменение создаёт основу для EVO-04: выбор операции при мутации сможет опираться
на тот же контракт, по которому проверяется готовый потомок.

## Контракт возможностей операции

`OperationCapabilities` описывает свойства, необходимые для построения и
проверки графа:

- роль операции: модель, преобразование, источник данных или неизвестная роль;
- допустимые входные и выходные типы данных;
- поддерживаемые типы задач;
- поддерживаемые устройства `cpu` и `cuda`;
- возможность сериализации;
- допустимое положение в графе;
- минимальное и максимальное число родителей;
- допустимость одинаковых родительских операций;
- поддержку нескольких входов;
- необходимость целевой переменной и обучения;
- метки операции.

Каталог расширения Industrial теперь содержит соответствующие поля в
`IndustrialOperationDeclaration`. Старые записи `catalog.json` остаются
совместимыми: средство разбора применяет явные значения по умолчанию. Для операций NumPy
по умолчанию заявлен `cpu`, для операций Torch — `cpu` и `cuda`. Ограничения
можно уточнять в записи конкретной операции без изменения проверяющего кода.

## Чистая модель графа

`GraphSpec` содержит:

- идентификатор графа;
- тип задачи;
- запрошенное устройство, если оно задано явно;
- требование сериализуемости;
- набор `GraphNodeSpec` с идентификаторами родителей и возможностями операций.

Оболочка `graph_spec_from_runtime` один раз восстанавливает граф GOLEM через
`PipelineAdapter`, извлекает сведения из каталога Industrial или метаданных
FEDOT и передаёт чистые значения в `validate_graph`.

Схема сериализации графа имеет версию `industrial_graph_spec@1`, а схема отчёта
— `industrial_graph_validation@1`.

## Полный отчёт проверки

`ValidationReport` содержит все обнаруженные `ValidationIssue`, а не только
первую причину отказа. Каждое нарушение включает устойчивый код, сообщение,
затронутые узлы и операции, а также дополнительные значения для диагностики.

Правила проверяют:

- пустой граф, повторяющиеся идентификаторы и отсутствующих родителей;
- самоссылки, циклы, число корней и связность;
- наличие первичных узлов;
- существование описания операции;
- совместимость с задачей, устройством и требованием сериализации;
- положение операции и число родителей;
- модель в корне графа;
- совместимость типов данных на каждом ребре;
- одинаковые ветви преобразований;
- смешение источников данных;
- положение `resample`;
- структуру `decompose` и `class_decompose`;
- объединение параллельных ветвей фильтрации.

Порядок нарушений детерминирован и не зависит от порядка узлов во входном
кортеже. Проверки структуры используют время `O(V + E)` и память `O(V + E)`, где
`V` — число узлов, а `E` — число рёбер. Проверка типов выполняется за `O(E)` при
небольшом фиксированном множестве типов данных.

## Граница совместимости

`IndustrialGraphVerifier` сохраняет вызываемый интерфейс прежнего
`GraphVerifier`: результатом `verify` и `__call__` остаётся логическое значение.
При этом свойство `last_report` хранит полный отчёт последней проверки.

`IndustrialEvoOptimizer` заменяет свой валидатор на эту оболочку до запуска
родительского конструктора. Если чистые правила не находят нарушений, оболочка
дополнительно вызывает прежний валидатор FEDOT. Его отказ получает отдельный
код `legacy_verifier_rejected`. Такая последовательность временно сохраняет
множество допустимых графов и одновременно делает расхождения наблюдаемыми.

Ожидаемые ошибки преобразования графа становятся
`graph_adaptation_failed`. Ошибки среды, например `OSError`, не перехватываются.

## Диагностика оптимизатора

Событие отклонения кандидата теперь может содержать
`validation_issue_codes`. Сводка EVO-01 дополнена счётчиком
`validation_issue_counts`, а отчёт Markdown — таблицей нарушений проверки.
Старые потребители сохраняют совместимость: новые поля необязательны, версия
`industrial_evolution_diagnostics@1` не изменена.

## Проверки

Модульные тесты проверяют:

- накопление независимых нарушений без раннего выхода;
- пустые графы, отсутствующих родителей, самоссылки и циклы;
- задачи, устройства, сериализуемость, положение и число родителей;
- совместимость типов каждого ребра;
- специальные ограничения `resample`, `decompose` и ветвей фильтрации;
- независимость результата от порядка узлов;
- отсутствие циклов в порождаемых ациклических графах;
- обязательное обнаружение самоссылки для произвольного идентификатора;
- однократное восстановление графа GOLEM;
- работу на реальном конвейере FEDOT;
- структурированный отказ прежнего валидатора;
- сохранение кодов нарушений в журнале и сводке оптимизатора;
- проверку новых полей каталога и ошибочных ограничений.

Целевой набор проверок:

```powershell
.venv\Scripts\python.exe -m pytest `
  tests/unit/integration/fedot/extensions `
  tests/unit/core/optimizer -q
```

Результат: 146 тестов пройдены.

## Ограничения этапа

- Прежний валидатор FEDOT пока остаётся дополнительным проверяющим слоем. Его
  правила будут удаляться только после анализа зарегистрированных расхождений.
- Для встроенных операций FEDOT возможности извлекаются из метаданных во время
  построения `GraphSpec`; каталог Industrial остаётся основным источником для
  операций расширения.
- Устройство проверяется только тогда, когда оно явно присутствует в контексте
  построения графа. Значения `auto` и `default` не создают ложных ограничений.
- EVO-03 не восстанавливает недопустимые графы и не меняет выбор мутаций. Эти
  задачи относятся к EVO-04.
- Ошибки `InvalidFitness`, обход Industrial-оптимизатора в регрессии и разбиение
  данных прогнозирования сохранены как отдельные исходные проблемы следующих
  этапов.
