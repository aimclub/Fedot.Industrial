# EVO-04: ограниченное планирование мутаций и восстановление графа

## Состояние этапа

Реализован и проверен структурный контур задачи #288. Через `FedotIndustrial`
прошли поиск и обучение итоговых моделей классификации, регрессии и
прогнозирования с включённым кэшем. Для этого явно применены переносимые
исправления к изолированной копии FEDOT на закреплённом коммите; установленный
пакет и штатная зависимость не изменялись. Последняя проверка описана ниже.
С 16 октября 2026 года число уникальных графов используется только для диагностики,
а не как требование повторить прежнее пространство поиска. Приёмка должна
опираться на качество и вычислительные затраты при сопоставимых условиях.
Проведённый короткий запуск не заменяет сравнение полных обученных популяций.
Этот документ не является основанием для включения планировщика по умолчанию.

## Что изменилось

Раньше GOLEM выбирал мутацию, случайным образом изменял граф и повторял попытки
после отказа проверяющего слоя. Теперь Industrial сначала строит ограниченный
набор допустимых решений, выбирает одно решение и применяет его один раз.

Пакет `fedot_ind.core.optimizer.mutation_planning` содержит чистые функции:

- `enumerate_mutation_plans`: перечисление замен, вставок, новых ветвей и удалений;
- `admissible_operations`: выбор допустимых замен для заданного узла;
- `apply_mutation_plan`: атомарное применение решения с повторной проверкой;
- `select_mutation_plan`: выбор по явно переданному начальному значению;
- `repair_graph`: ограниченное восстановление без изменения задачи и данных.

`MutationPlan` содержит подпись исходного `GraphSpec` и неизменяемые правки.
Если граф, контекст или возможности операций изменились, применение старого
плана возвращает `STALE_PLAN`. При отказе частично изменённый граф не выдаётся.

`mutation_runtime.py` связывает эти решения с FEDOT/GOLEM. Оболочка читает только
включённый набор операций фабрики, сохраняет ограничения первичных и вторичных
узлов и учитывает запреты `PipelineChangeAdvisor`. Параметры и метаданные
заменённого узла не переносятся на другую модель; неизменённые узлы копируются.
Общий родитель нескольких ветвей остаётся общим родителем, а не размножается.

При создании новой многозадачной операции с интерфейсом `InputData` явно
передаётся `task_type` из контекста графа. Схема расширения разрешает этот
параметр. Это не перенос настроек предыдущего узла: без него адаптер мог выбрать
первую задачу из каталога и обработать регрессионные значения как классы.
Параметры неизменённых узлов сохраняются, а встроенные операции FEDOT не
получают лишних параметров.

## Ограничения и совместимость

Восстановление удаляет повторную ссылку на одного родителя или обходит обычное
унарное преобразование, чтобы соблюсти ограничения глубины и размера. Оно не
исправляет циклы, неизвестные операции, несовместимые задачи, устройства и
контракты данных. Источники, специальные и многовходовые операции не
переписываются. Вставка перед первичным узлом использует существующий неявный
вход, а не создаёт новый источник данных.

Входные и выходные типы в метаданных означают поддерживаемые альтернативы.
Совместимость требует непустого пересечения, а не поддержки всех альтернатив
сразу. Итоговый граф всё равно проходит чистый валидатор и прежние правила FEDOT.
Особые правила удаления поддеревьев не подменяются обычным обходом узла.

`AddBranch` сохраняет существующее ребро и добавляет параллельный путь через
новую операцию с тем же родителем. Это не создание нового источника данных.
`DropPrimaryTransform` разрешён только при подтверждённом `RawInputSpec`, если
следующий узел принимает фактический тип входа и требования к цели соблюдены.
Контекст извлекается из штатного `TensorData` в целевой функции FEDOT, а не из
перечня типов, которые операция в принципе поддерживает. Для произвольного
производителя данных контекст не угадывается и производитель не вызывается.
Контекст сохраняется в плане; его изменение делает план устаревшим.

Поддержка многомодальных данных в возможностях операции сама по себе не делает
унарный граф многовходовым. Замены таких операций допустимы в подтверждённом
одновходовом графе; источники и специальные многовходовые структуры остаются
защищены. Создание ветвей для таких операций по-прежнему запрещено.
`single_edge` не поддерживается новым механизмом.
Пользовательские функции и изменение параметров выполняются один раз на копии
графа, после чего результат также проверяется. Для случайного агента веса
ограничиваются доступными действиями; обучаемый агент сохраняет собственный
выбор и получает отрицательное подкрепление при недопустимом действии.

Веса теперь сопоставляются именам мутаций и нормируются для включённого набора,
а не зависят от его порядка. Временная смена весов не затрагивает обучаемые
агенты и отменяется даже при исключении. Расширение популяции соблюдает общий
таймер и не повторяет поиск для родителя с пустым детерминированным набором планов.

Штатный `PipelineChangeAdvisor` теперь знает включённые расширения Industrial:
модели добавляются в список моделей, преобразования в список операций с данными.
Используется копия советника; исходный объект не меняется. Запреты источников,
пользовательских операций и специальных преобразований сохраняются. Советники
пользователя и их подклассы не подменяются. Это исправление действует и для
прежнего оператора мутации, независимо от включения нового планировщика.

Структурированные неудачи оценивания FEDOT передаются в диагностику Industrial
с исходным видом ошибки и сообщением, а не заменяются общим `InvalidFitness`.
Неизвестные целевые функции сохраняют прежнее поведение.

## Настройки

В `industrial_evolution_config@1` добавлен раздел:

```json
{
  "random_seed": 42,
  "mutation_planning": {
    "enabled": true,
    "max_candidates": 128,
    "max_repair_edits": 2,
    "max_nodes": 64
  }
}
```

Глубина и число родителей берутся из требований GOLEM. `max_candidates`
ограничивает суммарное число рассматриваемых структурных предложений при
подготовке входа и планировании одной мутации, а не отдельно для каждого вида.
Общее число вызовов мутации при построении популяции ограничивает существующий
`ResourceBudget`. Для функций пользователя дополнительно ограничена проверка
их результата; время работы самой функции этим бюджетом не ограничивается.

По умолчанию `enabled=false`: остаётся прежний оператор GOLEM, пока не завершена
полная проверка обучения. Новый механизм включается явно, как в примере выше.
Начальное значение
`random_seed` использует адреса кандидатов из EVO-02 и не зависит от UUID узлов.
Состояние глобальных генераторов восстанавливается после вызова.

Новые события `mutation_plan` содержат вид действия, состояние, число
проверенных и допустимых планов, число исправлений и коды отказов. Они не
увеличивают повторно счётчик попыток. В метаданных потомка сохраняются сам план,
исходный и подготовленный графы. Обратный вызов локальной диагностики не
сериализуется вместе с оператором для исполнителя.

## Выбор алгоритма

Рассматривались три подхода: прежние случайные повторы; полный перебор графов;
ограниченное перечисление локальных изменений. Выбран последний подход:
потоки предложений чередуются, одинаковые результаты исключаются, восстановление
жадно уменьшает превышение бюджета. Случайного поиска и отката по дереву решений
в чистом ядре нет.

При `V` узлах, `E` рёбрах, бюджете предложений `B` и бюджете исправлений `R`
обход и построение структурной подписи требуют `O(V+E)`. Стоимость планирования
ограничена `O(B * (V+E+C_validate))`, где `C_validate` учитывает правила проверки
графа. Память для сохранённых планов ограничена `B`, копия графа требует `O(V+E)`.
Жадное восстановление может потребовать `O(R * V * (V+E+C_validate))`; число
рассмотренных предложений дополнительно ограничено `B`. Метаданные возможностей
операций входят в стоимость сериализации и здесь не считаются бесплатными.

## Измерения

Проверка выполнена 5 октября 2026 года на Python 3.10.0 с FEDOT
`d1875e7a1ba49c94d13c51d97ec78829bf459ca8`. Изолированное окружение использует
часть системных зависимостей: scikit-learn 1.6.1 и Torch 2.2.0. Это не полностью
совпадает с версиями `pyproject.toml`; проверка в штатном окружении всё ещё нужна.

Сравнение находится в
`benchmark.industrial.experiments.mutation_planning`. Настройки вынесены в
`defaults.json`: три задачи, три начальных значения и 40 попыток для каждого.
Каждая попытка начинается с одинакового графа. Старый механизм получает одну
попытку без скрытых повторов. Для обоих механизмов действуют одни и те же чистые
правила и полный проверяющий слой FEDOT. Модели в этом сравнении не обучаются.

| Задача | Допустимые изменённые графы: раньше | Теперь | Уникальные графы: раньше / теперь | Разных операций: раньше / теперь |
|---|---:|---:|---:|---:|
| Классификация | 106/120, 88,3% | 120/120, 100% | 17 / 11 | 6 / 6 |
| Регрессия | 106/120, 88,3% | 120/120, 100% | 17 / 11 | 6 / 6 |
| Прогнозирование | 42/120, 35% | 107/120, 89,2% | 6 / 4 | 4 / 4 |

Исторический ориентир для повторной проверки на этом фиксированном наборе:
не менее 90% допустимых изменённых графов и сохранение набора используемых
операций. Это локальный критерий, выведенный из измеренного исходного уровня,
а не гарантия для произвольного пространства поиска. Следующий вывод о полном
сохранении разнообразия относится к прежнему критерию, отменённому 16 октября.
Полное сохранение
разнообразия графов **не достигнуто**: 11 вместо 17 для табличных задач и 4 вместо
6 для прогнозирования. Новые правки увеличили разнообразие по сравнению с первой
итерацией (8 и 3), но не устранили отставание. Для прогнозирования не достигнут
и ориентир в 90%: часть новых предложений отклоняет окончательная проверка FEDOT.
Перед включением по умолчанию требуется улучшить согласованность чистого
планировщика с этой проверкой и сравнить качество реальных популяций.

В последнем запуске `.local/evo04_mutation_final_task_context` 120 старых вызовов
занимали 0,122–0,187 с, новых 1,933–2,151 с. Новый механизм дороже; это единичный
замер без оценки погрешности
и прогрева, а не утверждение об ускорении. Его польза здесь — допустимость
предложений и ограниченная работа. Решение о кэшировании следует принимать
по профилю реального обучения, а не по этим малым графам.

Исторический EVO-01 в `.local/evo01_baseline_v5` показывал для классификации
1 принятого кандидата на 4 попытки и 8 оценок `InvalidFitness`. Это другой
уровень измерения, его нельзя напрямую сравнивать с таблицей структурных
предложений. Отсутствие наблюдавшихся популяций в том запуске также не означает
нулевого разнообразия реальных популяций.

## Предыдущие проверки API

Этот раздел сохраняет ход диагностики до применения переносимых исправлений.
Текущее состояние приведено в следующем разделе.

Удалён вызов `sys.setrecursionlimit(1000000000)` при импорте топологического
генератора: он глобально менял поведение процесса. После удаления повторный
запуск с прежним оператором мутаций перестал завершаться нативным переполнением
стека при сериализации задания Dask и сформировал отчёт с обычными ошибками.
Добавлен тест, запрещающий изменение этого глобального ограничения при импорте.
Это наблюдение объясняет воспроизведённое падение, но не доказывает причину всех
исторических аварий процесса.

Без переносимого исправления при штатно включённом кэше предсказаний FEDOT обращается к
`descriptive_id=None` в `PredictionsCache.load` и получает `TypeError`.
В проверочном запуске кэш явно отключён через `--without-prediction-cache`.
Это не изменение настройки библиотеки по умолчанию и не исправление самого
кэша. Без этого флага запуск в данном окружении не считается рабочим.

В `.local/evo04_api_extended_advisor` классификация и регрессия успешно прошли
композицию и обучение итогового пайплайна. Однако часть промежуточных кандидатов
получила `ExtensionContractError`: `bagging` при преобразовании обращался к
форме отсутствующей цели. Исправлена проверка отсутствующей цели; добавлены
тесты обучения и последующего преобразования неразмеченных данных через
адаптер расширений для классификации и регрессии. Окончательный повтор после
согласования `task_type` со схемой параметров выполнен штатной командой
`api_runner`, без отладочных подмен методов. Результаты находятся в
`.local/evo04_api_task_context_v2`:

| Сценарий | Состояние | Успешные оценки / ошибки оценивания | Итоговый пайплайн |
|---|---|---:|---|
| Классификация | Поиск и итоговое обучение завершены | 7 / 0 | `minirocket_extractor -> pdl_clf` |
| Регрессия | Поиск и итоговое обучение завершены | 7 / 0 | `quantile_extractor -> pdl_reg` |
| Прогнозирование | Отказ до оптимизатора | Не выполнялись | Не обучен |

В двух завершённых сценариях зарегистрировано по одному принятому потомку на
одну попытку. Это малый набор проверки работоспособности, а не исследование
качества моделей или доказательство устойчивости на полных бенчмарках.
Предыдущий запуск с передачей `task_type`, но ещё без разрешения этого параметра
в схеме (`.local/evo04_api_task_context`), завершился неудачно и не считается
подтверждением работоспособности.

До исправления временного разбиения прогнозирование останавливалось до запуска Industrial-оптимизатора:
`DataSourceSplitter` использует число объектов `TensorData` для обычного
разбиения. Единственная временная серия даёт один объект; деление с
`split_ratio=0.5` оставляет пустую часть. Нужно временное разбиение в FEDOT,
а не искусственное изменение формы данных или замена ряда демонстрационным.

Ограничение времени композиции не ограничивает последующее обучение итоговой
модели. Для связки MiniRocket и PDL регрессия оказалась существенно дольше
классификации; это нужно учитывать при ограничении ресурсов полного запуска.

`api_runner` сохраняет `verification_settings.json`, фактические
`*_api_config.json`, настройки набора, исходные сообщения ошибок и отчёты
JSON/Markdown. По умолчанию он не обучает модели. `--legacy` отключает только
новое планирование, не отменяя общие исправления совместимости.
После выполнения код возврата отличен от нуля при любой ошибке или отсутствии
диагностических артефактов: частичный успех не скрывается.
Каталог с диагностикой предыдущего обучения нельзя использовать для нового
проверочного обучения; файлы не удаляются, предлагается новый каталог.

В фактическом журнале Dask работает с одним исполнителем и четырьмя потоками,
хотя конфигурация примера запрашивает один поток. Соблюдение этой настройки
нужно проверить отдельно в контуре управления вычислительными ресурсами.
Эти запуски выполняются на CPU и не подтверждают работу CUDA.

## Переносимые исправления и повторная проверка

Добавлен пакет `fedot_ind.integration.fedot.compat`. Он содержит два обычных
исправления `.patch`, манифест с исходным коммитом FEDOT и контрольными суммами,
команды предварительной проверки, явного применения и проверки результата.
Инструкция находится в `fedot_ind/integration/fedot/compat/README.md`.
Ни импорт, ни проверочный запуск не устанавливают исправления автоматически.
Несовпадение версии, изменение затрагиваемого файла или неверная контрольная
сумма останавливают выполнение. Применение проверено и на отдельной чистой копии
`.local/worktrees/fedot-evo04-compat-smoke`.

Исправлены следующие причины отказов:

- `Operation.fit` терял `descriptive_id` при передаче в `predict_for_fit`.
  Теперь идентификатор сохраняется; при его отсутствии операция не обращается
  к кэшу, а не использует общий ключ `None`.
- `DataSourceSplitter` делил единственный временной ряд по оси объектов.
  Теперь контрольный горизонт отделяется по последней временной оси.
  Обучение видит только предшествующую историю; внешняя контрольная цель
  не используется для обучения или внутреннего выбора модели.
- Граница Industrial повторно обрезала уже разделённый ряд и игнорировала
  явную контрольную цель. Теперь обе части сохраняются. Для полного ряда
  без заданной цели сохраняется прежнее отделение объявленного горизонта.
- Прежние временные реализации FEDOT получали `TensorData`, хотя требовали
  `InputData`. Добавлена явная граница форматов и нормализован выход `ridge`.
  Неподдерживаемые многомерные сценарии не заменяются искусственными данными.
- Модель расширения принимала длину обучающей цели за горизонт прогноза.
  В схеме Industrial объявлен `forecast_length`; исправление FEDOT передаёт
  его из задачи только расширениям, которые разрешают этот параметр.
  Несогласованный явный горизонт отклоняется.
- Советник считал `lagged_ridge_forecaster` преобразованием `lagged` по
  совпадению части имени. Теперь специальные ограничения относятся только
  к `lagged` и `sparse_lagged`, не мешая замене прогнозных моделей.

Возможности встроенных временных операций также учитывают ограничение
`max_parents=1` для тега `non_lagged`. Это позволяет планировщику исключить
недопустимые ветви, не ослабляя окончательный валидатор FEDOT.

Общий повтор выполнен штатным `api_runner`, без подмен методов:

```powershell
$env:PYTHONPATH="$PWD/.local/worktrees/fedot-evo02-test;$PWD"
.local/evo02-tests/Scripts/python.exe -m benchmark.industrial.experiments.mutation_planning.api_runner `
  --output-dir .local/evo04_api_compat_verified --execute `
  --compatibility-worktree .local/worktrees/fedot-evo02-test
```

В `verification_settings.json` записаны версия FEDOT и контрольные суммы.
Проверка сверяет также фактически импортируемую копию FEDOT. Кэш предсказаний
не отключён; все три сценария завершились с кодом возврата 0.

## Диагностика, бюджет и параллельные признаки: 16 октября

Планировщик перебирает только семейства действий, которые включены и имеют
положительный вес. Проверки чередуются между семействами, узлами и позициями
вставки. Явное смещение каталога сохраняет воспроизводимость и устраняет
постоянное предпочтение его начала при малом бюджете. Это не гарантия, что каждый
малый бюджет найдёт допустимый вариант: усечение отмечается явно.
Неудачные проверки и повторы результатов тоже расходуют бюджет.
Восстановление графа уменьшает оставшийся бюджет; оно не получает скрытый
дополнительный набор попыток после пользовательской функции.

`MutationExecution.planning` содержит `industrial_mutation_search@1`:
лимит, число проверок, включённые семейства, смещение, признак усечения,
сводки причин и ограниченный перечень решений. Для каждой проверки видны правка,
операция, узлы, состояние и этап: `planning`, `advisor` или `runtime`.
Видны, в частности, несовместимость вида операции, типов данных и задачи,
неподтверждённый вход, повтор операции, нарушение бюджета, отказ советника
и окончательного проверяющего слоя. Число решений равно числу рассмотренных
кандидатов; диагностика не запускает дополнительный неограниченный перебор.
Структурный отчёт сохраняет причины отсева и всегда возвращает `not_assessed`
для приёмки качества и затрат.

Добавлены `AddPrimaryBranch` и `DropPrimaryBranch`: два независимых
преобразования одного подтверждённого входа могут подавать табличные признаки
в общую операцию; одну неразделяемую первичную ветвь можно затем удалить,
не удаляя последний признаковый вход. Поддержка мультимодальных данных операцией
больше не означает запрета такого однородного сценария. Но разные источники,
специальные операции, фильтры, объединение предсказаний моделей и прогнозные
ветвления этим не разрешаются. Новое первичное ветвление ограничено задачами
классификации и регрессии, двумя входами и однозначно табличными выходами
преобразований; общие ограничения числа узлов, глубины и родителей сохраняются.
Неоднозначные альтернативные выходные типы не угадываются.

Исправление `aligned_feature_fusion.patch` добавлено третьим в пакет совместимости.
Оно сохраняет порядок одинаковых индексов признаковых ветвей. Прежний
`intersect1d` сортировал индексы без перестановки строк признаков.
Повторные метки объектов отклоняются явно. Исправление не заявляет поддержку
произвольного сопоставления разных источников. Все три исправления применены
штатной командой к новой чистой копии `.local/worktrees/fedot-evo04-feature-smoke`;
контрольные суммы совпали.

Реальные конвейеры из `quantile_extractor_torch`, `quantile_extractor` и PDL
проверены для классификации и регрессии: обучение, предсказание на новых объектах,
сохранение неотсортированных индексов, целей и исходного массива.

Новый `quality_runner` выполняет короткую проверку одношагового поиска:
48 синтетических объектов, два начальных значения, три попытки на режим,
включая исходный конвейер. Обучение, выбор по проверочной части и окончательная
тестовая проверка разделены. В обоих режимах совпадают данные, разбиение и бюджет
попыток. Ошибки кандидатов сохраняются. Время включает предложение, обучение
и выбор; отдельно измеряется итоговое предсказание. `python_tracemalloc`
учитывает выделения Python, а не всю память процесса, PyTorch или CUDA.

Первый запуск `.local/evo04_quality_cost_20261016` завершил все восемь режимов:
в четырёх парах итоговое качество совпало. Временные затраты нового механизма
выше: в зависимости от пары около 1,1–3,8 раза. Это единичные короткие измерения,
включающие различное число успешных обучений и возможную загрузку реализаций;
они не доказывают ни ускорения, ни ухудшения полного поиска. Низкое качество

Проверка приёмки возможна только при явных допусках качества и ограничениях затрат.
Отсутствующие пары, неудачи, разные бюджеты и несопоставимые области измерения

прогнозирование в новом сравнении качества, штатные зависимости и CUDA

`benchmark/industrial/experiments/mutation_planning/README.md`.

Заключительный запуск находится в `.local/evo04_quality_cost_20261016_verified`:

## Исправление `hankelisation -> ridge`: 16 октября

### Причина

Воспроизведена ошибка настройки: при горизонте 8 оценщик сравнивал цель
из 8 значений с предсказанием длины 72 и выдавал штраф
`9223372036854775808`. Одного прямого обучения было недостаточно для обнаружения:
`ridge` успешно запоминал одну строку, целевым вектором которой была вся история.

`TensorData` хранит один ряд как `(1, T)`. Обычный путь расширений сохраняет
число объектов и передаёт преобразователю только массив признаков. Он не вызывал
`transform_for_fit` и не переносил оконные цели и индексы. Многозадачная
`hankelisation` также не объявляла `forecast_length`, поэтому её обёртка выводила
горизонт из длины цели. Это нарушение границы данных, а не недостаточная
сложность Ridge или ансамбля.

Уточнение прежнего описания: конвейер создаёт `LaggedAR`, зарегистрированный как
`lagged_forecaster`. Он наблюдался в общем журнале запуска, завершившегося выбором
`hybrid_ensemble_forecaster`, но не является внутренней ветвью современной
реализации этого ансамбля. Современные ветви используют общий механизм окон
прогнозирования напрямую.

### Исправления

- Обновлено переносимое `temporal_evaluation.patch`: типизированные
  `TemporalTransformInput` / `TemporalTransformOutput` отделяют оконный путь
  от обычного преобразования признаков. Он разрешён только по сочетанию тега
  `ts_to_table`, задачи прогнозирования и исходного временного типа.
- История одного одномерного ряда передаётся явно; отложенная цель в запрос
  не включается. При обучении проверяются согласованные формы `(M, W)` и
  `(M, H)` и уникальные индексы окон. При прогнозировании разрешено ровно одно
  окно без цели. Устаревшие метаданные и отпечатки источника очищаются.
  Проверка сохранения числа объектов у остальных преобразований не ослаблена.
- `hankelisation` переиспользует `build_hankel_trajectory_transform`.
  Устранены скрытое изменение ширины окна и смещение признаков относительно
  целей при шаге больше единицы или горизонте 1. Число обучающих строк равно
  `floor((T - W - H) / S) + 1`. Прогноз всегда использует последние `W` значений,
  даже если шаг обучения не делит длину истории. Достаточно контекста длины `W`.
  Общий исторический класс `HankelMatrix` не изменён.
- `LaggedAR` определяет длину времени, а не первой оси массива, и открывает
  собственную область регистрации при `predict`. Вложенные области и очистка
  при исключении проверены. Поддержка нескольких рядов или каналов не заявляется.
- Отдельно исправлено создание равных весов `HybridEnsembleForecaster`:
  при короткой истории они теперь находятся на устройстве и имеют тип,
  заданные `TensorDevicePolicy`, а не всегда создаются на CPU.

`forecast_length`; в `deepar_model` вход GRU находится на CPU, а параметры
модели на CUDA. Причины подтверждены отдельным воспроизведением и сохранены в
`.local/evo04_remaining_forecast_failures.log`. Они не маскируются общим статусом
и остаются следующими задачами EVO-04. Dask по-прежнему создаёт четыре потока
при запросе одного.

Этот общий запуск выполнен до завершающих исправлений определения длины ряда
в `LaggedAR` и устройства равных весов. После них отдельно повторены настройка
и прогноз, реальный путь `lagged_forecaster` и весь набор регрессионных тестов.

## OKHS-FDMD И DeepAR: Исправления Исполнения

### OKHS-FDMD

Служебный `forecast_length`, переданный FEDOT из задачи, попадал через
`normalize_okhs_fdmd_params` в конструктор `OKHSFDMDForecaster`, который принимает
`forecast_horizon`. Теперь нормализация проверяет положительный целый горизонт
и его совпадение с задачей, затем исключает служебный ключ из параметров модели.
Исходный словарь не изменяется. Неизвестные параметры модели не отбрасываются
молча. Проверены конфликт, некорректные значения, целые значения NumPy,
эквивалентность спецификаций и повторная нормализация через Hypothesis.

После устранения ошибки конструктора выявлена следующая причина отказа:
обёртка `FractionalDMD._select_modes` сокращала матрицу мод и спектр оператора,
но не обновляла сохранённые собственные значения и векторы внутренней модели.
При прогнозировании сравнивались, например, 35 собственных значений и 28 мод.
Теперь все три связанных массива обновляются согласованно. Правила отбора мод
и критерий устойчивости не менялись. Для фиксированного отбора, не оставляющего
устойчивых мод, сохраняется явная ошибка; проверка не заменяет её запасной моделью.

### DeepAR

История и скрытые состояния могли находиться на CPU, хотя параметры GRU/LSTM
уже находились на CUDA. Также сохранённое поле устройства устаревало после
переноса модели, а статистики масштабирования и квантили не переносились
вместе с параметрами.

Теперь входы, скрытые состояния, обучающие и проверочные пакеты приводятся
к фактическим устройству и типу параметров сети. Средние значения, коэффициенты
масштабирования и квантили зарегистрированы как непостоянные буферы PyTorch;
они следуют за `model.to(...)`, не меняя прежний состав `state_dict`.
Построение начального скрытого состояния не создаёт граф градиентов.
Загрузчик больше не изменяет переданные пользователем признаки и цели.
Переданное скрытое состояние проверяется через `is None`, а не логическое
преобразование многозначного тензора.

Пройдены настоящие обучение и прогнозирование для CPU и CUDA, GRU и LSTM,
проверочной выборки и переноса модели в `float64`. Проверены буферы нормального
распределения и распределения Коши, прогнозы квантилей и неизменность входов.
Настройка глобального устройства и отключение CUDA не применялись.

### Отдельная Проверка Обеих Моделей

Артефакт `.local/evo04_forecast_models_preflight_final/verification.json`
содержит версии среды, контрольные суммы изменённых реализаций, исходную
историю, отложенные значения, прогнозы, метрики и сведения о совместимости FEDOT.
Использованы данные того же `tiny_forecasting`: 96 значений, 88 для обучения
и 8 отложенных, начальное значение генератора 42. Для обеих моделей взяты
настройки из пакета по умолчанию; DeepAR действительно обучался 100 эпох.

| Модель | Исполнение | Горизонт | Фактическое устройство | RMSE |
|---|---|---:|---|---:|
| `okhs_fdmd_forecaster` | Обучение и прогноз завершены | 8 | CPU | 14612478,4331 |
| `deepar_model` | Обучение и прогноз завершены | 8 | `cuda:0`, `float32` | 0,9351 |

Это доказательство исправления исполнения, **не приёмка качества**. Результат
OKHS-FDMD неприемлем для данного ряда и требует отдельного разбора устойчивости
и восстановления прогноза. Большие конечные значения не объявляются хорошим
прогнозом и не обрезаются ради прохождения проверки. Настройка правил устойчивости
и изменение математического метода в это исправление не входят.
Для масштаба: простое повторение последнего значения обучающей истории даёт
RMSE `0,4606` на тех же восьми отложенных значениях. Это один короткий сценарий,
а не оценка качества моделей на полном бенчмарке.

Внешний `compute_config.backend='cpu'` пока не является общим ограничением
устройства каждой вложенной нейросети. В этой проверке штатный автоматический
выбор DeepAR действительно использовал RTX 4080. Схема расширения пока не
принимает явный `device` для `deepar_model`; выбор CPU/CUDA отдельно проверен
через прямой API DeepAR. Управление устройством через внешний API остаётся
отдельной задачей, а не скрытым переключением в данном исправлении.
