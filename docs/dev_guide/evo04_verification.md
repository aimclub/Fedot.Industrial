# EVO-04: ограниченное планирование мутаций и восстановление графа

## Состояние этапа

Реализован и проверен структурный контур задачи #288. Через `FedotIndustrial`
прошли поиск и обучение итоговых моделей классификации и регрессии при явно
отключённом кэше предсказаний. Прогнозирование пока блокирует ошибка разбиения
данных в используемой версии FEDOT. Разнообразие структур также ещё не достигло
исходного уровня. Этот документ не является основанием для закрытия issue или
включения нового планировщика по умолчанию.

## Что изменилось

Раньше GOLEM выбирал мутацию, случайным образом изменял граф и повторял попытки
после отказа проверяющего слоя. Теперь Industrial сначала строит ограниченный
набор допустимых решений, выбирает одно решение и применяет его один раз.

Пакет `fedot_ind.core.optimizer.mutation_planning` содержит чистые функции:

- `enumerate_mutation_plans`: перечисление замен, вставок, новых ветвей и удалений;
- `admissible_operations`: выбор допустимых замен для заданного узла;
- `apply_mutation_plan`: атомарное применение решения с повторной проверкой;
- `select_mutation_plan`: выбор по явно переданному начальному значению;
- `repair_graph`: ограниченное восстановление без изменения задачи и данных.

`MutationPlan` содержит подпись исходного `GraphSpec` и неизменяемые правки.
Если граф, контекст или возможности операций изменились, применение старого
плана возвращает `STALE_PLAN`. При отказе частично изменённый граф не выдаётся.

`mutation_runtime.py` связывает эти решения с FEDOT/GOLEM. Оболочка читает только
включённый набор операций фабрики, сохраняет ограничения первичных и вторичных
узлов и учитывает запреты `PipelineChangeAdvisor`. Параметры и метаданные
заменённого узла не переносятся на другую модель; неизменённые узлы копируются.
Общий родитель нескольких ветвей остаётся общим родителем, а не размножается.

При создании новой многозадачной операции с интерфейсом `InputData` явно
передаётся `task_type` из контекста графа. Схема расширения разрешает этот
параметр. Это не перенос настроек предыдущего узла: без него адаптер мог выбрать
первую задачу из каталога и обработать регрессионные значения как классы.
Параметры неизменённых узлов сохраняются, а встроенные операции FEDOT не
получают лишних параметров.

## Ограничения и совместимость

Восстановление удаляет повторную ссылку на одного родителя или обходит обычное
унарное преобразование, чтобы соблюсти ограничения глубины и размера. Оно не
исправляет циклы, неизвестные операции, несовместимые задачи, устройства и
контракты данных. Источники, специальные и многовходовые операции не
переписываются. Вставка перед первичным узлом использует существующий неявный
вход, а не создаёт новый источник данных.

Входные и выходные типы в метаданных означают поддерживаемые альтернативы.
Совместимость требует непустого пересечения, а не поддержки всех альтернатив
сразу. Итоговый граф всё равно проходит чистый валидатор и прежние правила FEDOT.
Особые правила удаления поддеревьев не подменяются обычным обходом узла.

`AddBranch` сохраняет существующее ребро и добавляет параллельный путь через
новую операцию с тем же родителем. Это не создание нового источника данных.
`DropPrimaryTransform` разрешён только при подтверждённом `RawInputSpec`, если
следующий узел принимает фактический тип входа и требования к цели соблюдены.
Контекст извлекается из штатного `TensorData` в целевой функции FEDOT, а не из
перечня типов, которые операция в принципе поддерживает. Для произвольного
производителя данных контекст не угадывается и производитель не вызывается.
Контекст сохраняется в плане; его изменение делает план устаревшим.

Поддержка многомодальных данных в возможностях операции сама по себе не делает
унарный граф многовходовым. Замены таких операций допустимы в подтверждённом
одновходовом графе; источники и специальные многовходовые структуры остаются
защищены. Создание ветвей для таких операций по-прежнему запрещено.
`single_edge` не поддерживается новым механизмом.
Пользовательские функции и изменение параметров выполняются один раз на копии
графа, после чего результат также проверяется. Для случайного агента веса
ограничиваются доступными действиями; обучаемый агент сохраняет собственный
выбор и получает отрицательное подкрепление при недопустимом действии.

Веса теперь сопоставляются именам мутаций и нормируются для включённого набора,
а не зависят от его порядка. Временная смена весов не затрагивает обучаемые
агенты и отменяется даже при исключении. Расширение популяции соблюдает общий
таймер и не повторяет поиск для родителя с пустым детерминированным набором планов.

Штатный `PipelineChangeAdvisor` теперь знает включённые расширения Industrial:
модели добавляются в список моделей, преобразования в список операций с данными.
Используется копия советника; исходный объект не меняется. Запреты источников,
пользовательских операций и специальных преобразований сохраняются. Советники
пользователя и их подклассы не подменяются. Это исправление действует и для
прежнего оператора мутации, независимо от включения нового планировщика.

Структурированные неудачи оценивания FEDOT передаются в диагностику Industrial
с исходным видом ошибки и сообщением, а не заменяются общим `InvalidFitness`.
Неизвестные целевые функции сохраняют прежнее поведение.

## Настройки

В `industrial_evolution_config@1` добавлен раздел:

```json
{
  "random_seed": 42,
  "mutation_planning": {
    "enabled": true,
    "max_candidates": 128,
    "max_repair_edits": 2,
    "max_nodes": 64
  }
}
```

Глубина и число родителей берутся из требований GOLEM. `max_candidates`
ограничивает суммарное число рассматриваемых структурных предложений при
подготовке входа и планировании одной мутации, а не отдельно для каждого вида.
Общее число вызовов мутации при построении популяции ограничивает существующий
`ResourceBudget`. Для функций пользователя дополнительно ограничена проверка
их результата; время работы самой функции этим бюджетом не ограничивается.

По умолчанию `enabled=false`: остаётся прежний оператор GOLEM, пока не завершена
полная проверка обучения. Новый механизм включается явно, как в примере выше.
Начальное значение
`random_seed` использует адреса кандидатов из EVO-02 и не зависит от UUID узлов.
Состояние глобальных генераторов восстанавливается после вызова.

Новые события `mutation_plan` содержат вид действия, состояние, число
проверенных и допустимых планов, число исправлений и коды отказов. Они не
увеличивают повторно счётчик попыток. В метаданных потомка сохраняются сам план,
исходный и подготовленный графы. Обратный вызов локальной диагностики не
сериализуется вместе с оператором для исполнителя.

## Выбор алгоритма

Рассматривались три подхода: прежние случайные повторы; полный перебор графов;
ограниченное перечисление локальных изменений. Выбран последний подход:
потоки предложений чередуются, одинаковые результаты исключаются, восстановление
жадно уменьшает превышение бюджета. Случайного поиска и отката по дереву решений
в чистом ядре нет.

При `V` узлах, `E` рёбрах, бюджете предложений `B` и бюджете исправлений `R`
обход и построение структурной подписи требуют `O(V+E)`. Стоимость планирования
ограничена `O(B * (V+E+C_validate))`, где `C_validate` учитывает правила проверки
графа. Память для сохранённых планов ограничена `B`, копия графа требует `O(V+E)`.
Жадное восстановление может потребовать `O(R * V * (V+E+C_validate))`; число
рассмотренных предложений дополнительно ограничено `B`. Метаданные возможностей
операций входят в стоимость сериализации и здесь не считаются бесплатными.

## Измерения

Проверка выполнена 5 октября 2026 года на Python 3.10.0 с FEDOT
`d1875e7a1ba49c94d13c51d97ec78829bf459ca8`. Изолированное окружение использует
часть системных зависимостей: scikit-learn 1.6.1 и Torch 2.2.0. Это не полностью
совпадает с версиями `pyproject.toml`; проверка в штатном окружении всё ещё нужна.

Сравнение находится в
`benchmark.industrial.experiments.mutation_planning`. Настройки вынесены в
`defaults.json`: три задачи, три начальных значения и 40 попыток для каждого.
Каждая попытка начинается с одинакового графа. Старый механизм получает одну
попытку без скрытых повторов. Для обоих механизмов действуют одни и те же чистые
правила и полный проверяющий слой FEDOT. Модели в этом сравнении не обучаются.

| Задача | Допустимые изменённые графы: раньше | Теперь | Уникальные графы: раньше / теперь | Разных операций: раньше / теперь |
|---|---:|---:|---:|---:|
| Классификация | 106/120, 88,3% | 120/120, 100% | 17 / 11 | 6 / 6 |
| Регрессия | 106/120, 88,3% | 120/120, 100% | 17 / 11 | 6 / 6 |
| Прогнозирование | 42/120, 35% | 107/120, 89,2% | 6 / 4 | 4 / 4 |

Предлагаемый ориентир для повторной проверки на этом фиксированном наборе:
не менее 90% допустимых изменённых графов и сохранение набора используемых
операций. Это локальный критерий, выведенный из измеренного исходного уровня,
а не гарантия для произвольного пространства поиска. Полное сохранение
разнообразия графов **не достигнуто**: 11 вместо 17 для табличных задач и 4 вместо
6 для прогнозирования. Новые правки увеличили разнообразие по сравнению с первой
итерацией (8 и 3), но не устранили отставание. Для прогнозирования не достигнут
и ориентир в 90%: часть новых предложений отклоняет окончательная проверка FEDOT.
Перед включением по умолчанию требуется улучшить согласованность чистого
планировщика с этой проверкой и сравнить качество реальных популяций.

В последнем запуске `.local/evo04_mutation_final_task_context` 120 старых вызовов
занимали 0,122–0,187 с, новых 1,933–2,151 с. Новый механизм дороже; это единичный
замер без оценки погрешности
и прогрева, а не утверждение об ускорении. Его польза здесь — допустимость
предложений и ограниченная работа. Решение о кэшировании следует принимать
по профилю реального обучения, а не по этим малым графам.

Исторический EVO-01 в `.local/evo01_baseline_v5` показывал для классификации
1 принятого кандидата на 4 попытки и 8 оценок `InvalidFitness`. Это другой
уровень измерения, его нельзя напрямую сравнивать с таблицей структурных
предложений. Отсутствие наблюдавшихся популяций в том запуске также не означает
нулевого разнообразия реальных популяций.

## Проверка API и оставшиеся ограничения

Удалён вызов `sys.setrecursionlimit(1000000000)` при импорте топологического
генератора: он глобально менял поведение процесса. После удаления повторный
запуск с прежним оператором мутаций перестал завершаться нативным переполнением
стека при сериализации задания Dask и сформировал отчёт с обычными ошибками.
Добавлен тест, запрещающий изменение этого глобального ограничения при импорте.
Это наблюдение объясняет воспроизведённое падение, но не доказывает причину всех
исторических аварий процесса.

При штатно включённом кэше предсказаний FEDOT обращается к
`descriptive_id=None` в `PredictionsCache.load` и получает `TypeError`.
В проверочном запуске кэш явно отключён через `--without-prediction-cache`.
Это не изменение настройки библиотеки по умолчанию и не исправление самого
кэша. Без этого флага запуск в данном окружении не считается рабочим.

В `.local/evo04_api_extended_advisor` классификация и регрессия успешно прошли
композицию и обучение итогового пайплайна. Однако часть промежуточных кандидатов
получила `ExtensionContractError`: `bagging` при преобразовании обращался к
форме отсутствующей цели. Исправлена проверка отсутствующей цели; добавлены
тесты обучения и последующего преобразования неразмеченных данных через
адаптер расширений для классификации и регрессии. Окончательный повтор после
согласования `task_type` со схемой параметров выполнен штатной командой
`api_runner`, без отладочных подмен методов. Результаты находятся в
`.local/evo04_api_task_context_v2`:

| Сценарий | Состояние | Успешные оценки / ошибки оценивания | Итоговый пайплайн |
|---|---|---:|---|
| Классификация | Поиск и итоговое обучение завершены | 7 / 0 | `minirocket_extractor -> pdl_clf` |
| Регрессия | Поиск и итоговое обучение завершены | 7 / 0 | `quantile_extractor -> pdl_reg` |
| Прогнозирование | Отказ до оптимизатора | Не выполнялись | Не обучен |

В двух завершённых сценариях зарегистрировано по одному принятому потомку на
одну попытку. Это малый набор проверки работоспособности, а не исследование
качества моделей или доказательство устойчивости на полных бенчмарках.
Предыдущий запуск с передачей `task_type`, но ещё без разрешения этого параметра
в схеме (`.local/evo04_api_task_context`), завершился неудачно и не считается
подтверждением работоспособности.

Прогнозирование останавливается до запуска Industrial-оптимизатора:
`DataSourceSplitter` использует число объектов `TensorData` для обычного
разбиения. Единственная временная серия даёт один объект; деление с
`split_ratio=0.5` оставляет пустую часть. Нужно временное разбиение в FEDOT,
а не искусственное изменение формы данных или замена ряда демонстрационным.

Ограничение времени композиции не ограничивает последующее обучение итоговой
модели. Для связки MiniRocket и PDL регрессия оказалась существенно дольше
классификации; это нужно учитывать при ограничении ресурсов полного запуска.

`api_runner` сохраняет `verification_settings.json`, фактические
`*_api_config.json`, настройки набора, исходные сообщения ошибок и отчёты
JSON/Markdown. По умолчанию он не обучает модели. `--legacy` отключает только
новое планирование, не отменяя общие исправления совместимости.
После выполнения код возврата отличен от нуля при любой ошибке или отсутствии
диагностических артефактов: частичный успех не скрывается.
Каталог с диагностикой предыдущего обучения нельзя использовать для нового
проверочного обучения; файлы не удаляются, предлагается новый каталог.

В фактическом журнале Dask работает с одним исполнителем и четырьмя потоками,
хотя конфигурация примера запрашивает один поток. Соблюдение этой настройки
нужно проверить отдельно в контуре управления вычислительными ресурсами.
Эти запуски выполняются на CPU и не подтверждают работу CUDA.

Перед закрытием #288 остаются исправление кэша и временного разбиения FEDOT,
повтор трёх задач в штатном окружении зависимостей и достижение критериев
допустимости и разнообразия графов. Новый механизм остаётся явно включаемым.
