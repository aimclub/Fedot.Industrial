# FED-02: проверка контракта внешних операций FEDOT

## Назначение

Этап FED-02 укрепляет существующий пакет `fedot.extensions` в ветке FEDOT,
не создавая второй реестр операций. Изменения вошли в Pull Request
[`aimclub/FEDOT#1462`](https://github.com/aimclub/FEDOT/pull/1462); версия всего
цикла, использованная в INT-01:
`d1875e7a1ba49c94d13c51d97ec78829bf459ca8`.

Основные цели этапа:

- разделить внешние модели и преобразования на уровне спецификаций,
  возможностей и исполнительных адаптеров;
- проверять манифесты и параметры до запуска пользовательского кода;
- обеспечить атомарную регистрацию и восстановление состояния после выхода
  из области регистрации;
- выбирать совместимую сигнатуру до вызова функции и выполнять пользовательский
  код ровно один раз;
- проверить настоящий конвейер `TensorData` с внешним преобразованием и моделью.

## Реализованный контракт

`ExtensionManifest` по-прежнему служит единственной точкой описания расширения.
Поле `models` сохраняет прежнее положение среди аргументов, а новое поле
`transforms` добавлено в конец структуры. Для преобразований введены
`ExternalTransformSpec` и `TransformCapabilities`; модели продолжают использовать
`ExternalModelSpec` и `ModelCapabilities`.

Регистрация хранится в `ContextVar`. `extension_scope` наследует родительские
записи, не допускает перекрытия имён и восстанавливает предыдущее состояние даже
при исключении. Пакетная функция `register_extensions` сначала строит и проверяет
полный план, а затем одной операцией публикует его. Режим `dry_run=True` возвращает
план без изменения реестра и без вызова фабрик.

Вызов фабрик и методов состоит из двух шагов: `inspect.signature(...).bind(...)`
выбирает подходящую форму аргументов, после чего функция вызывается один раз.
Исключение из пользовательского кода преобразуется в `ExtensionContractError`,
но сохраняется как причина. Оно не считается признаком несовместимой сигнатуры
и не приводит к повторному вызову.

Для `TensorData` добавлены разные стратегии модели и преобразования. Внешний код
получает собственную копию массива или тензора. Преобразование возвращает новые
признаки, а модель записывает прогноз. Интеграционный тест обучает конвейер
`StandardScaler -> LinearRegression` на CPU без подмены встроенного каталога.

## Проверки

Целевой набор на Python 3.10 и 3.11:

```text
196 passed
```

В него входят тесты `fedot.extensions`, фабрики операций, настоящий конвейер
`TensorData` и подключение расширений к репозиторию операций.

Расширенный набор на Python 3.11:

```text
290 passed
```

Он дополнительно охватывает все тесты `tests/core/operations` и
`tests/core/repository`.

Независимая проверка добавила 42 варианта инвариантов: положение конфликта в
пакете регистрации, независимость плана от порядка, откат вложенной области,
единственный вызов при `TypeError`, `ValueError` и `RuntimeError`, а также
разделение моделей и преобразований при обнаружении и создании операций.

Дополнительные проверки:

- `compileall` для всех изменённых модулей и тестов проходит;
- `git diff --check` проходит;
- `autopep8 --diff` не выявил содержательных изменений; вывод касается только
  различий между окончаниями строк LF и CRLF в рабочей копии;
- в изменённом коде нет `eval` и `bind_partial`.

## Состояние общего набора тестов

Команда `pytest` без ограничений собирает одновременно текущий каталог `tests`,
устаревший каталог `test` и старый встроенный модуль `fedot.industrial`. Сборка
старых частей останавливается на отсутствующих дополнительных зависимостях
`pywt` и `fastcore`, а также на удалённых API прежней версии FEDOT.

Для текущего каталога `tests` без старого `tests/industrial` базовый коммит FED-01
имел 14 падений. После FED-02 осталось 12 тех же падений, не связанных с
расширениями. Два устранённых сбоя относились к несогласованному срезу данных в
тесте PCA и к отсутствующему `return self` в
`PipelineOperationRepository.from_available_operations`.

На этапе FED-02 проверка целостности зависимостей была ограничена составом
локальных окружений. В INT-01 зафиксированный снимок установлен через `uv`,
проверен по PEP 610 и прошёл `pip check` в отдельном окружении.

## Ограничения

Этап не проверяет выполнение на GPU, сериализацию обученных внешних операций,
многомодальные входы и перенос области регистрации в сторонние процессы.
Новый поток или процесс должен получить контекст явно. `Pipeline.fit` переносит
контекст в собственный поток, который создаётся при использовании ограничения
времени.

Манифесты являются неизменяемыми структурами верхнего уровня, однако вложенные
значения параметров следует считать неизменяемыми по соглашению. Типы и диапазоны
отдельных гиперпараметров пока не входят в схему `ModelHyperparamsSchema`.
