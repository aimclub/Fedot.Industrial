# Эволюционный поиск и явные исполнители

[Результаты запусков и разбор затрат, 27 октября 2026](results_20261027.md).

Пример запускает настоящий `IndustrialEvoOptimizer`: строит графы, обучает их
на TRAIN, оценивает на трёх внутренних разбиениях, выбирает модель и только после
полного поиска вычисляет итоговую метрику TEST. Это не повтор приёмки EVO-04.
Её отрицательный результат и выключенный по умолчанию планировщик не меняются.
Планирование мутаций включено явно только в конфигурации этого примера.

## Данные и конфигурация

| Задача | Набор из установленного sktime | Проверка во время поиска |
| --- | --- | --- |
| Классификация | ACSF1, распознавание электроприборов по временным рядам | Три стратифицированных разбиения официального TRAIN |
| Регрессия | Tecator, спектральная регрессия из TSER | Три разбиения официального TRAIN |
| Прогнозирование | Airline, месячные пассажироперевозки | Три последовательных горизонта по 12 месяцев внутри TRAIN; последние 12 месяцев отложены |

Нормализация классификации и регрессии обучается отдельно внутри каждого
разбиения. TEST не выбирает настройки, модели или исполнителя. Короткие пробные
запуски `--pilot` не загружают официальный TEST классификации/регрессии и не
вычисляют итоговую метрику. Airline поставляется одним рядом: отложенный хвост
не входит в обучающие разбиения. Сырые данные не добавляются в git.

Параметры находятся в
`benchmark/industrial/experiments/evolution_parallelism/defaults.json`.
Основной протокол: 15 **эволюционных поколений после начальной популяции**,
целевой размер популяции 8, четыре процесса исполнителей, seed 42;
для BLAS/OpenMP задан один поток,
120 секунд на кандидата и 1100 секунд на подготовку и поиск.
Срок остановки без улучшения задан явно: не меньше общего бюджета поиска,
а не унаследованные пять минут GOLEM. Все ограничения сохраняются в `limits.json`.
Внешний ограничитель даёт всему процессу не более 1200 секунд, включая
окончательное обучение и построение отчётов, затем останавливает только
собственное дерево процессов. Принудительное завершение — ошибка, не успешный
полный поиск. Подтверждение остановки может потребовать до 10 секунд.

Одинаковые ограничения OMP/MKL/OpenBLAS/NumExpr задаются до импорта библиотек
в отдельном процессе каждого режима. Глобальные настройки вызывающей программы
не меняются. Значения Torch до/после и версии записываются в артефакты.
Гиперпараметры моделей одинаковы между исполнителями, в том числе леса из
500 деревьев. Данные и параметры выбираются по стоимости пробных TRAIN-запусков,
а не по качеству на TEST.

Во время оценки кандидата внутренний `dask.compute` использует синхронный
планировщик. Окончательное обучение — отдельный этап со штатными внутренними
механизмами операций; ограничение BLAS/OpenMP не является общим запретом на
создание потоков Python. На графиках ресурсов конец поиска отмечен пунктиром,
поэтому затраты последующего обучения и диагностики можно отличить от поиска.

Старый дисковый кэш признаков отключён явно у `quantile_extractor`,
`fourier_basis` и `wavelet_basis`: ключ по форме массива не изолирует разные
разбиения данных. `use_cache` для `wavelet_basis` объявлен в схеме расширения;
значение по умолчанию библиотеки не изменено. Прерванные замеры с этим кэшем
не входят в сравнение.

## Запуск

Нужны зависимости проекта и совместимый профиль FEDOT из
`.github/actions/fedot-compat/action.yml`. Для встроенных отчётов дополнительно:

```powershell
python -m pip install "bokeh>=3.1,<3.5" "matplotlib>=3.7"
```

Предварительная проверка без данных, моделей, клиентов и файлов:

```powershell
python -m examples.release_1_0.evolution --task classification --backend dask --lifecycle search
```

Три режима с теми же настройками. Для каждого запуска нужна новая папка:

```powershell
python -m examples.release_1_0.evolution --task classification --backend sequential --execute --output-dir examples/artifacts/cloud_bundle/evolution_parallelism/clf_sequential
python -m examples.release_1_0.evolution --task classification --backend process --execute --output-dir examples/artifacts/cloud_bundle/evolution_parallelism/clf_process
python -m examples.release_1_0.evolution --task classification --backend dask --lifecycle search --execute --output-dir examples/artifacts/cloud_bundle/evolution_parallelism/clf_dask
```

Для остальных задач используйте `--task regression` и `--task ts_forecasting`.
`--pilot --generations 1` — только проверка исполнения, не подтверждение 15 поколений.

## Жизненный цикл Dask

- `--lifecycle batch`: прежний путь, отдельный частный кластер для каждой оценки
  популяции. Запуск, остановка и отчёты каждой популяции учитываются во времени.
  Сам выбор `--backend dask` не гарантирует ускорения. Для одного управляемого
  сеанса на поиск явно укажите `--lifecycle search`.
- `--lifecycle search`: вызывающий код явно открывает `DaskEvaluationSession`
  и передаёт его оценкам через `dask_session_scope`. После оценки клиент остаётся
  доступен; закрывает его создавший сеанс внешний блок. Это управляемый сеанс,
  **не автоматическое заимствование произвольного глобального Client**.
  Сеанс выделен одному поиску и последовательным пакетам его кандидатов;
  совместное исполнение независимых внешних заданий на этих работниках
  не входит в контракт примера.
- Обычный последовательный/процессный запуск не создаёт Dask-клиент или кластер.
- Ошибки модели не повторяются. В конфигурации Dask разрешена одна повторная
  попытка при распознанной потере работника; время кандидата не сбрасывается.
- Ограничения отдельной оценки не охватывают окончательное обучение FEDOT.
  Последовательный режим проверяет время между вызовами, не прерывает `fit`.
  Поэтому в примере есть отдельный внешний ограничитель всего процесса.

Отдельный исполняемый пример проверяет ограничения без обучения моделей:

```powershell
python -m examples.release_1_0.evolution.limits --execute --output-dir examples/artifacts/cloud_bundle/evolution_parallelism/contracts
```

Он показывает кооперативное превышение срока в последовательном режиме,
остановку уже начатого вызова в отдельном процессе, потерю собственного работника
Dask с одной успешной повторной попыткой и сохранение доступности клиента после
оценки. Эти искусственные проверки контрактов не входят в измерения ускорения.

## Два сравнения

Первое сравнение выполняет по 15 поколений. Совпадение начального значения само
по себе не доказывает одинаковый объём работы: отчёт сверяет параметры, TRAIN,
разбиения и **мультимножество** фактически оценённых конфигураций. Ускорение
одинаковой работы не вычисляется, если эти проверки не пройдены.

Дополнительный протокол `--protocol time --budget-seconds N` задаёт всем режимам
одинаковое время на подготовку и поиск, включая запуск процесса и кластера.
Он показывает число завершённых уникальных конфигураций, повторы, ошибки,
поколения и лучшую внутреннюю оценку. Нельзя сравнивать время только тела поиска
одного режима со временем запуска и поиска другого.

## Артефакты и мониторинг

Всё записывается локально рядом в выбранной папке:

- `config.json`, `implementation.json`, `environment.json`, `source.json`:
  настройки, контрольные суммы исходников, версии, TRAIN и разбиения;
- `coordinator_events.jsonl`, `completed_evaluations.json`, `generations.json`:
  постепенное сохранение событий, принятых результатов и поколений;
- `traces/`: оценки кандидатов и включительное/исключительное время операций;
- `process_samples.csv`: CPU, потоки и память собственного дерева процессов;
- `dask/`: встроенный `performance_report.html`, `task_stream.html`, исходные
  `task_stream.json`, `memory_samples.csv`; профиль работника сохраняется,
  если Dask смог собрать достаточно образцов;
- `dask_diagnostics.json`: состояние диагностики, включая пустой профиль;
- `selected_graph.json`, `predictions.csv`, `summary.json`, `supervisor.json`:
  выбранный граф, итоговые предсказания, метрики и полный срок выполнения.

`startup_seconds` в исходном `summary.json` измеряет только явное открытие
одного управляемого сеанса Dask. Ноль для `lifecycle=batch` не означает
отсутствия суммарных затрат на запуск кластеров; они входят в `search_wall_seconds`.

Dask видит оценку целого кандидата как задачу. Время отдельных операций графа
измеряется дополнительным локальным инструментированием с восстановлением
методов после вызова. Исключительное время не суммирует повторно вложенный
`predict_for_fit`. Сумма RSS процессов — не уникальная физическая память и не PSS;
измерение с интервалом 0,2 секунды может пропустить короткий пик.
`MemorySampler` показывает память работников, а `process_samples.csv` включает
также главный процесс эксперимента. Время операций относится к оценке кандидатов;
окончательное обучение учитывается отдельно в `refit_seconds`.

Встроенные HTML-отчёты предназначены для браузера. Их устройство описано в
[Dask: Capture diagnostics](https://distributed.dask.org/en/latest/web.html#capture-diagnostics)
и [Diagnosing performance](https://distributed.dask.org/en/latest/diagnosing-performance.html).
Большие HTML/JSON/CSV не коммитятся; папка `cloud_bundle` уже исключена из git.

Сводные таблицы, динамика поиска и графики CPU/памяти строятся отдельно, без
повторного обучения. Передайте все сравниваемые папки; пилоты будут отклонены:

```powershell
python -m examples.release_1_0.evolution.report examples/artifacts/cloud_bundle/evolution_parallelism/clf_sequential examples/artifacts/cloud_bundle/evolution_parallelism/clf_process examples/artifacts/cloud_bundle/evolution_parallelism/clf_dask --output-dir examples/artifacts/cloud_bundle/evolution_parallelism/reports/classification
```

Рядом с рисунками сохраняются исходные CSV и `report_manifest.json` с контрольными
суммами результатов. `same_workload_speedup` остаётся пустым, если конфигурации,
их кратность или оценки отличаются либо не хватает полного журнала попыток.
`paired_work.csv` проверяет каждую пару, а не только сравнение с последовательным
режимом. Отношение времени разных поисковых
траекторий не следует называть ускорением одинаковой работы.
